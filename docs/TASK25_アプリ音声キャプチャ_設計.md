# タスク25 アプリ単位の音声キャプチャ — 設計

対象ブランチ: `feature/task25-app-audio-capture`
状態: **設計・準備のみ。実装は未着手。**

Discord / OBS「アプリケーション音声キャプチャ」と同じことをする。
**選んだウィンドウのプロセスが鳴らしている音だけ**を取り込んで配信に乗せる。

---

## 1. なぜ ffmpeg だけでは無理か

タスク22の音声取り込み（[streamer_core.py:341](../streamer_core.py) 以降）は **dshow 一本**で、
「OSに見えている録音デバイスを丸ごと1本取る」方式。ステレオミキサーを選べば PC の音は取れるが、
それは**ミックス後の全体音**であり、**デバイスという粒度ではアプリを分離できない**。

Discord / OBS が使っているのは WASAPI の**プロセスループバック**:

- `ActivateAudioInterfaceAsync(VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK, ...)`
- `AUDIOCLIENT_ACTIVATION_PARAMS.ActivationType = AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`
- `ProcessLoopbackMode = PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`

**単位はデバイスではなく PID。** ffmpeg にこの API のバインディングは無く、dshow にプロセスという概念も無い。
引数をどう工夫しても到達できない。したがって**ネイティブの補助 exe が要る**。

## 2.5 フェーズP0の実測結果（2026-09-06 / 合格）

`native/app_audio_capture/src/main.cpp` を実装（agy へ委譲）し、**このPCで実際に音を取れることを確認した。**

### 測り方

`ffplay` に 440Hz の正弦波を鳴らさせ、そのPIDを対象に4秒キャプチャ。
**同時に、鳴っていない無関係プロセス（explorer.exe）も4秒キャプチャして比較した。**

| 対象 | frames | peak | rms | 推定基本周波数 |
|---|---|---|---|---|
| ffplay（440Hzを再生中） | 192000 (4.00s) | 176 | **122.4** | **440.0 Hz** |
| explorer.exe（無音・同時刻） | 192000 (4.00s) | 1 | **0.5** | — |

- **対象からは 440.0Hz がぴたりと復元できた。** プロセスループバックは実機で動く
- **同時刻に鳴っていた 440Hz は、無関係プロセス側へ一切漏れていない**（rms 0.5 = ±1LSB 相当）。
  分離はできている。これがこの機能の全目的なので、ここが確認できた意味は大きい

### 確定した事実

- **`Initialize` は 16bit PCM で通った。** 32bit float へのフォールバックは（この環境では）使われない
- 出力バイト数は 4秒 × 48000 × 2ch × 2byte = **768000 と厳密に一致**した
- 終了コードと stderr ログは契約どおり動作

### 観測（P1で確かめ直すこと）

**無音の explorer.exe からも、4秒ぶんのデータが途切れず届いた。**
P0 には壁時計基準の無音埋めをまだ入れていないので、これは **API 側が無音パケットを
供給していた**ことを意味する。無音埋めが不要かもしれない、という示唆ではあるが、
**explorer が音声セッションを開いていただけの可能性がある。**
「一度も音を出していないプロセス」でも同じか、P1で必ず測り直すこと。ここを楽観して外すと
同期がじわじわずれる形で跳ね返る。

### ビルド周りで直したこと

- `build.bat` に **`/utf-8`** を追加。main.cpp は UTF-8(BOM無)で、付けないと MSVC が cp932 と
  誤認して C4819 が出る。日本語コメントの2バイト目が 0x5C の文字は行継続として食われうるので、
  警告では済まない可能性がある
- `.bat` を CRLF に統一し、`.gitattributes` に `*.bat text eol=crlf` を追加
- **`'vswhere.exe' は認識されていません` は `vcvars64.bat`（Microsoft側）が出す無害なノイズ。**
  こちらのスクリプトの不具合ではない（実測で確認済み）。build.bat にその旨をコメントで残した

## 2.6 無音時の挙動 — 実測して設計を変更（2026-09-06）

設計当初「プロセスループバックは対象が無音の間パケットを返さないので、壁時計基準の
無音埋めが必須」と書いた。**実測したら違った。** P1の仕様を測定結果に合わせて変える。

| # | 条件 | 生成サンプル | 期待 | 差 |
|---|---|---|---|---|
| 1 | 音声セッションを一度も開いていないプロセス / 4秒 | 768,000 byte = **4.000s** | 4.000s | **0** |
| 2 | 鳴る2s → 無音3s → 鳴る2s / 7秒 | 6.990s | 7.000s | -10ms |
| 3 | 完全無音のプロセス / **30秒** | 5,760,000 byte = **30.000s** | 30.000s | **0** |

**API は対象が無音でも無音パケットを供給し続ける。ドリフトは蓄積しない。**
測定3で 30 秒回して誤差ゼロなので、これは偶然ではない。

測定2では、音の先頭を基準にすると「2.10s の音 → 2.90s の無音」で、素材の
「2.00s → 3.00s」に対して 100ms バケットの量子化誤差の範囲。**無音区間が詰められて
前にずれる、という当初懸念した壊れ方は起きていない**（ffplay の起動に約0.7秒かかるため、
絶対時刻で見ると全体が後ろにずれて見える。これは測定側の事情）。

### P1 での扱い

- **壁時計基準の無音埋めを「主たる仕組み」にはしない。** 実測で不要と分かったものを
  常時走らせると、二重に埋めて逆にずれる
- **ただし保険としてのガードは入れる。** イベント待ちが続けて空振りする（デバイス切替、
  フォーマット変更、セッションリセット）ときだけ無音で埋め、**埋めたことを必ずログに出す**。
  ドリフトは目に見えないまま悪化するので、発火したことが分かる形にしておく
- 測定はいずれも既定の出力デバイスが有効な状態で行った。**キャプチャ中にデバイスが
  切り替わった場合は未測定**。`AUDCLNT_E_DEVICE_INVALIDATED` の処理は P1 で入れる

## 3. データの流れ

```
[対象ウィンドウ] --hwnd--> GetWindowThreadProcessId --pid-->
      |
      |  ※ hwnd→pid は enumerate_capture_windows() が既に返している
      |     (streamer_core.py:641 付近 / タスク23で追加済み)
      v
  app_audio_capture.exe --pid <PID>
      |
      |  stdout = 生PCM (s16le / 48000Hz / 2ch / インターリーブ)
      |  ※ OSパイプで直結する。Python はバイトを一切コピーしない:
      |     helper = Popen(..., stdout=PIPE)
      |     ffmpeg = Popen(..., stdin=helper.stdout)
      v
  取り込み側 FFmpeg
      -f ddagrab|gdigrab ...            入力0: 映像
      -f s16le -ar 48000 -ac 2 -i pipe:0  入力1: アプリ音   ★新規
      -f dshow -i audio=...               入力2以降: マイク / 従来ループバック
      -filter_complex "...amix..."
      -f mpegts pipe:1
      |
      v
  Python relay --> 永続シンク FFmpeg (pipe:0) --> HLS / RTMP
```

### 経路を stdin(`pipe:0`) にした理由

取り込み側 FFmpeg は **stdout を MPEG-TS の出口に使っているが、stdin は現在 `DEVNULL` で空いている**
（`stdin=subprocess.DEVNULL, stdout=subprocess.PIPE` の形。streamer_core.py:3625 / 3810 / 4324 / 4494 など）。
ここに流し込めば、名前付きパイプも TCP も要らず、中継スレッドも増えない。

代替案（採らない）:
- 名前付きパイプ `\.\pipe\...` — 経路が増える割に利点が無い
- `tcp://127.0.0.1:PORT?listen=1` — ヘルパー異常時の切り離しは楽だが、ポート確保と競合処理が要る

**ただし `stdin` が塞がるので、将来 stdin を使う別機能と衝突しないか実装時に確認すること。**

## 4. ヘルパー exe の契約

`native/app_audio_capture/app_audio_capture.exe`

### 引数

| 引数 | 既定 | 意味 |
|---|---|---|
| `--pid <N>` | 必須 | 対象プロセスID |
| `--mode include\|exclude` | `include` | プロセスツリーを含める/除く |
| `--rate <N>` | `48000` | サンプリングレート |
| `--channels <N>` | `2` | チャンネル数 |
| `--probe` | — | 1秒だけ試して結果を stderr に出し即終了（UIの事前チェック用） |

### 出力

- **stdout**: 生PCM のみ。ヘッダもログも一切混ぜない
- **stderr**: 1行1イベント。`[AppAudio] ...` 接頭辞（既存の `log_print` と揃える）
- **終了コード**: `0`=正常 / `1`=引数不正 / `2`=Activate失敗 / `3`=対象プロセス消滅 / `4`=OSがAPI未対応

### 必須要件: 無音の埋め

**これを外すと確実に破綻する。** プロセスループバックは、**対象アプリが鳴らしていない間パケットを返さない。**
生PCM入力の PTS はサンプル数から生成されるので、無音区間でバイトが流れないと
**その分だけ音が映像より前にずれ続ける**（OBS も同じ処理を内部に持っている）。

- 単調増加のサンプルクロックを持ち、壁時計より出力サンプル数が遅れていたらゼロで埋める
- **起動直後から即座に流し始める**こと。対象が無音でも待たない
  （`pipe:0` 入力の FFmpeg はデータが来るまでストリームを確定できない。streamer_core.py:197 / 2589 の実測メモと同根の罠）

### 実装時に実測で確定させること

- **`GetMixFormat()` はこの活性化では使えない。** `WAVEFORMATEX` を明示指定して `Initialize` する。
  float32 と s16 のどちらが通るかは実機で確かめ、必要なら exe 側で s16le へ変換して出す
- `AUDCLNT_STREAMFLAGS_LOOPBACK | AUDCLNT_STREAMFLAGS_EVENTCALLBACK` の併用が必須（イベント駆動が要求される）

理由: 音が取れないことより配信が落ちることの方が事故として重い。

## 6. 落とし穴（着手前に読む）

1. **ウィンドウの PID ＝ 音を出すプロセス、とは限らない。**
   UWP / ストアアプリはウィンドウが `ApplicationFrameHost.exe` に属し、PID がフレームホストを指す。
   ツリー include でも取り漏らす。UI 側で「取れなかった」ことを検出して伝える必要がある
2. **ブラウザ・Discord はマルチプロセス。** 音は子プロセス（オーディオサービス）が出す。
   `INCLUDE_TARGET_PROCESS_TREE` が必須。それでもツリー外のサービスへ出す構成のアプリは取れない
3. **無音埋め必須**（4節）
4. **ヘルパーが落ちると FFmpeg が EOF を見て送出ごと止まる。** 監視して再起動するか、
   Python 側で無音を注ぎ続けるか、どちらを取るか実装前に決める
5. **`-vf` と `-filter_complex` は併用できない**（タスク22・23と同じ罠）。
   音声入力が3本になるとフィルタは必ず `filter_complex` 経路になる
6. **`.gitignore` が `*.exe` を全除外している**（74行目）。ビルド成果物がコミットされないのは正しいが、
   **リリース同梱（`build_exe.py` / `VRC_Media_Streamer.spec`）では明示的に拾う**必要がある
7. **未署名 exe はウイルス対策ソフトに誤検知されうる。** 配布時の注意書きが要る

## 9. 代替案（案A）— 実装せずに今日使える方法

VB-CABLE を入れ、Windows の「設定 → システム → サウンド → 音量ミキサー」で
**対象アプリの出力先だけを `CABLE Input` に変える**。
既存の `live_audio_loopback_device` に `CABLE Output` を選べば、そのアプリの音だけが乗る。
`is_loopback_candidate()` は既に `cable output` を候補として拾う（streamer_core.py:347 付近）。

欠点: VB-CABLE の導入が要る / その間アプリの音が自分のスピーカーから消える
（Voicemeeter か「このデバイスを聴く」で二重化は可能）/ アプリの選択が本アプリの UI ではなく Windows 側になる。

**このタスクが完成するまでの回避策として、ユーザー向けドキュメントに書いておく価値がある。**

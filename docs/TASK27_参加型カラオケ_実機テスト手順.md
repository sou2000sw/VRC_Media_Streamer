# タスク27 参加型カラオケ・セッション — 実機テスト手順

対象ブランチ: `feature/task27-karaoke-session`
設計の正本: `karaoke_session_design.md`（Antigravity の brain 側）

自動テストと実測で確認できたところは §1 に書いてある。
**ここに残っているのは、実機（本物のマイク・本物の回線・VRChat）でしか測れないもの**だけ。

---

## 0. 前提

### 0-1. 用意するもの

| もの | 理由 |
|---|---|
| ホストPC（本体を動かす） | — |
| スマホ 1台（できれば 2台） | 参加者役。2台あればデュエットとPANが試せる |
| **参加者側のイヤホン** | **必須。** 無いとハウリングして何も分からなくなる |
| VRChat（ヘッドセット or デスクトップ） | 最終的な聞こえ方の確認 |

### 0-2. トンネルを有効にすること

**参加者は必ず `https://` のトンネルURLから開く。**
ブラウザは `https://` か `localhost` でしかマイクを許可しないため、
LANの `http://192.168.x.x` では **マイクが取れない**（画面にもその旨が出る）。

これが今回いちばん踏みやすい落とし穴。テストが始まらないときは、まずここを疑う。

### 0-3. 受付を開ける

ホスト画面 → **「カラオケ参加」タブ** → ホスト卓 →
**「カラオケ受付を有効にする」にチェック**。

チェックが入っていないと `/ws/audio_session` は 403 を返し、参加者は繋がらない
（既定はオフ。知らないうちに他人の声が乗らないようにするため）。

## 1. 自動テスト・実測で**確認済み**のこと（実機で測り直さなくてよい）

| 項目 | 実測値 |
|---|---|
| 名前付きパイプ → FFmpeg | 440Hz 2秒 = **96,000フレーム**が欠落なく到達 |
| WS→ジッタバッファ→ミキサ→PAN→遅延→録音 の通し | ピーク **L=10000 / R=0**（PANが効いている） |
| 遅延ライン 500ms | 先頭400msのピーク **0**（効いている） |
| ミキサの時間軸 | 1秒で **50刻み**（壁時計から逆算するので自己補正する） |
| **ライブ音声配信 × カラオケの通し** | **HLSに歌声が乗る（max_volume −9.1dB / AAC 44.1kHz 2ch）** |
| filter_complex の妥当性 | 実FFmpeg 8.1.2 でパース成功 |
| カラオケ未使用時のFFmpegコマンド | 従来と**完全一致**（4通りの構成で固定） |
| 別オリジンからのホスト卓POST | **403**（参加者は自分を承認できない） |
| ゲストの `GET /api/karaoke` | 参加者一覧を返さない |
| カラオケ無効時の `/ws/audio_session` | **403** |
| 承認前に送られた音声 | 受信時点で破棄（バッファに溜まらない＝承認した瞬間に噴き出さない） |
| 送りつけ（規定の2倍超） | 接続を切断 |
| 有効／無効の往復 | ミキサが正しく再起動し、参加者は切断される |
| ホスト卓のスライダ | 400msの更新で要素が作り直されない（ドラッグが切れない） |

## 2. 実機で測ること

### 2-1. 参加できるか（いちばん基本）

| 操作 | 期待 |
|---|---|
| スマホでトンネルURLを開く →「カラオケ参加」タブ | 「マイクをつなぐ」ボタンが押せる |
| 名前を入れて「マイクをつなぐ」 | ブラウザがマイク許可を聞いてくる → 許可 |
| — | 状態バッジが **「挙手中（承認待ち）」** になる |
| 「手を挙げる」 | ホスト卓に名前と **挙手中** バッジが出る |
| ホストが「許可」 | スマホ側が **ON AIR**（赤・点滅）になる |
| スマホに向かって喋る | ホスト卓の **VUメーターが動く** |

> ✅ 記録すること: 挙手からホスト卓に出るまでの体感（1秒以内が期待値）

### 2-2. 遅延と音質（ここが本題）

`低遅延 40ms` と `安定 120ms` の両方で測る。

| 測ること | 記録 |
|---|---|
| 参加者画面の **Ping / ゆらぎ** の表示 | ___ ms / ___ ms |
| 手拍子してから VRChat で聞こえるまで（体感） | ___ 秒 |
| 「途切れ」の回数（ホスト卓の `buf ○○ms / 途切れ○○` 表示） | ___ 回 / 5分 |
| 声が割れないか（入力ゲインを 1.0 で） | ○ / × |
| モバイル回線（Wi-Fi を切って 4G/5G）でも保つか | ○ / × |

> 上り **約 768kbps** を使う（48kHz/16bit/モノラル）。
> モバイル回線でどうなるかは**未測定**。ここは実機でしか分からない。

> 途切れが多いなら **遅延モードを「安定 120ms」** に。
> それでも駄目なら回線側の問題。

### 2-3. 手元モニター（歌えるか）

| 操作 | 期待 |
|---|---|
| **イヤホンを着けて** サイドトーンを 30〜50% に上げる | 自分の声が耳に返る／音程が取りやすい |
| サイドトーンを上げた状態で**イヤホンを外す** | ハウリングする（＝警告が正しい。すぐ戻すこと） |
| 伴奏ファイルを選んで「再生」 | 手元で伴奏が鳴る |
| 「伴奏（手元で聴く音量）」を動かす | 自分に聞こえる伴奏だけが変わる |
| 「伴奏（配信へ送る音量）」を動かす | 配信側の伴奏だけが変わる（手元は変わらない） |
| 伴奏を鳴らしながら歌う | **VRChat側で伴奏と歌がズレていない**（← 最重要） |

> この使い方（手元伴奏をブラウザの中で混ぜて送る）なら、出発時点で貼り合わさって
> いるので**原理的にズレない**。ズレたら実装の不具合なので報告すること。

### 2-4. ホスト卓（配信を止めずに操作できるか）

**すべて配信しながら**動かして、配信が途切れないことを確認する。

| 操作 | 期待 |
|---|---|
| 歌声マスター音量 | VRChat側の歌の音量だけ変わる／**映像も音も途切れない** |
| リバーブ なし→弱→中→強 | 響きが増える／途切れない |
| PAN を L / C / R | VRChat側で左右に動く（ステレオで聴くこと） |
| 参加者ごとの音量 | その人だけ変わる |
| ミュート | その人の声だけ止まる／他は流れ続ける |
| 退出 | その人が切断され、スマホ側に理由が出る |
| 遅延モード切替 | 途切れない（一瞬バッファし直す） |

### 2-5. 遅延補正（ホストが伴奏を鳴らす場合）

参加者が手元伴奏を使わず、**ホスト側で伴奏を鳴らす**構成のとき。

| 操作 | 期待 |
|---|---|
| 伴奏をホストで再生しながら歌ってもらう | 歌が伴奏より**遅れて**聞こえるはず |
| 遅延補正を **マイナス方向**へ動かす | 歌が前に出てきて合う |
| 合った値を記録 | ___ ms |
| 補正を動かしている間 | **配信が途切れない** |

> ±500ms の範囲で足りるかを見る。足りなければ下駄（現在500ms）を増やす必要がある。

### 2-6. 複数人（デュエット）

スマホ2台で同時に参加する。

| 操作 | 期待 |
|---|---|
| 2人とも許可する | 両方 ON AIR、VUが独立して動く |
| 片方を L100、もう片方を R100 | VRChat側で**左右に分かれて**聞こえる |
| 2人同時に歌う | 音が割れない（割れるならマスター音量を下げる） |
| 8人まで入れてみる（可能なら） | 9人目が「満員です」で断られる |

### 2-7. 録音

| 操作 | 期待 |
|---|---|
| 「セッション録音」を押す | ボタンが「録音停止 (00:12)」に変わり時間が進む |
| 数分歌って停止 | `recordings\karaoke_YYYYMMDD_HHMMSS.wav` が出来る |
| その WAV を再生 | 歌が入っている／48kHz ステレオ／**PANが反映されている** |

> 録音は **ミックス済みの歌声バスだけ**。ホスト側の伴奏（PC音声）は入らない。
> 伴奏も残したいなら、参加者の手元伴奏を「配信へ送る」に乗せておくこと。

### 2-8. 荒らし・事故の想定

| 操作 | 期待 |
|---|---|
| 承認していない人が喋り続ける | 配信に**一切乗らない** |
| その人を後から許可する | **溜まっていた過去の音が噴き出さない**（今の声から始まる） |
| 「承認制」のチェックを外す | 繋いだ人が即 ON AIR になる（意図どおりか確認して、すぐ戻す） |
| 参加者がスマホの画面を消す／ブラウザを閉じる | ホスト卓から消える／配信は止まらない |
| 参加者が圏外になる | しばらくして消える／配信は止まらない |
| **PIN（Webパスワード）を設定して**参加を試す | 正しいPINでのみ入れる。違うPINは「合言葉（PIN）が違います」 |

### 2-9. 落ちたときの挙動

| 操作 | 期待 |
|---|---|
| 配信を止める → もう一度始める | 参加者は**繋がったまま**、自動で音が戻る |
| ホストPCで本体を終了 | 参加者側が切断される／**パイプのハンドルが残らない** |
| 本体をタスクマネージャで強制終了 → 再起動 | 同名パイプの掴み損ねで起動不能にならない |

## 3. 配布物（EXE）での確認

開発環境ではなく **ビルドした EXE** でも同じことを 1 周する。

```bat
python build_exe.py
```

| 見ること | 理由 |
|---|---|
| マイクを繋いだ瞬間に落ちないか | `karaoke_ws` は関数内で遅延importしている。`--hidden-import` で明示済みだが、**取りこぼすと落ちるのはこの瞬間** |
| `recordings` フォルダが **EXEの隣**に出来るか | onefile の展開先に書くと終了時に消える。APP_DIR を使うようにしてある |
| VRCBeacon の中（プラグイン）で「カラオケ参加」タブが動くか | オリジンが `beacon-plugin://` になる。AudioWorklet の Blob URL が塞がれたら ScriptProcessor へ退避する経路が働くはず（**未測定**） |

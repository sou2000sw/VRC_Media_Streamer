# タスク23 画面共有 — 実機テスト手順

対象ブランチ: `feature/task23-screen-share`

**ホスト側の送出（モニター配信・ウィンドウ配信とも）は実測で確認済み。**
この手順書が確かめたいのは、まだ未確認の以下3つ。

1. VRChatワールド内で実際に見えるか
2. TopazChat併用時の実遅延（会話が成立する範囲か）
3. 配信中の負荷（CPU / GPU）

## ★ 開始前に必ず読む（事故防止）

**ストリームキーは実質パスワードで、映り込むと配信を乗っ取られる。**
UIは既定で伏せ字表示にしているが、目のアイコンの **「表示」** ボタン
（ツールチップ:「ストリームキーを含む本物のURLを表示します（画面共有中は注意）」）を押した状態のまま
**モニター全体**を共有すると、アプリ自身のウィンドウごと本物のURLが配信に乗る。

- モニター全体を共有する前に、**「表示」を押していないこと**（伏せ字のままであること）を確認する
- Windows の集中モード（通知オフ）を入れる。通知バナーは容赦なく映る
- パスワードマネージャ・メール・DMのウィンドウを閉じる
- **迷ったら「ウィンドウ」指定を使う。** 対象ウィンドウ以外は映らないので事故が起きにくい

現状、**キャプチャ開始前のプレビュー確認は未実装**。上記は人間の目視が最後の防波堤になる。

## フェーズ1: ローカル単体確認（VRChat不要・トンネル無し）

VRChatを起動する前に、ホスト側だけで壊れていないことを確かめる。

### 1-1. 起動

```bash
python gui_streamer.py --no-tunnel --port 8123
```

ブラウザで `http://localhost:8123` を開く。

### 1-2. キャプチャ対象の列挙

1. 「設定」タブ → **「画面共有（このPCからのみ）」** カードを開く
2. **「一覧を再取得」** を押す

| 確認すること | 期待 |
|---|---|
| トーストの表示 | 「ディスプレイN件、ウィンドウM件を検出しました」 |
| 対象モニターの中身 | `ディスプレイ1 (2560x1440)` のように**実際の解像度**が入る |
| 対象ウィンドウの中身 | 今開いている**可視ウィンドウだけ**が並ぶ（最小化中のものは出ない） |
| 日本語ウィンドウ名 | 文字化けしない |
| 同名ウィンドウ | あれば「⚠ 同名あり」が付く |

★列挙には数秒かかる（ffmpeg を実起動してディスプレイを数えるため。実測3.4秒）。
結果は60秒キャッシュされるので、モニターを繋ぎ替えたら「一覧を再取得」を押すこと。

APIを直接見る場合（**localhost からのみ**通る）:

```bash
curl -s http://localhost:8123/api/capture_sources | python -m json.tool
```

### 1-3. モニター配信

1. 対象を **「モニター」** にして、ディスプレイを選ぶ
2. 解像度 `1280x720` / fps `20` / ビットレート `4000` で **「適用」**
3. 再生モードのピルから **「画面共有」** を選ぶ

| 確認すること | 期待 |
|---|---|
| ステータス | `streaming` / `Screen capture` |
| UIのプレビュー | 選んだモニターの内容が映る（数秒遅れる） |
| マウスカーソル | 「マウスカーソルを含める」のON/OFFが効く |
| セグメント生成 | `hls_output/` に `.ts` が増え続ける |

ログの確認:

```bash
findstr /C:"path=screen_capture" vrc_media_streamer.log
```

`[Player] Encoder path=screen_capture source=display display=0 window='' fps=20 size=1280x720 b:v=4000k`
のような行が1本出る。

生成物を実測で確かめる（**目視だけで済ませない**）:

```bash
ffprobe -v error -show_entries stream=codec_name,width,height,r_frame_rate -of csv hls_output/seg_00005.ts
```

→ `h264,1280,720,20/1` が返ること。音声デバイスを設定していれば `aac` も並ぶ。

### 1-4. ウィンドウ配信

1. 対象を **「ウィンドウ」** にして、適当なウィンドウ（メモ帳など）を選び「適用」
2. そのウィンドウを動かす・前面/背面を入れ替える

| 確認すること | 期待 |
|---|---|
| 映る内容 | **選んだウィンドウだけ**。他のウィンドウやデスクトップは映らない |
| 縦長・変形ウィンドウ | 潰れず、上下（左右）に黒帯が入って収まる |
| ステータス | `streaming` / `Screen capture` |

### 1-5. ★異常系（ここが今回いちばん壊れやすい）

| やること | 期待する挙動 |
|---|---|
| 配信中に対象ウィンドウを**閉じる** | ステータスが `error` になり、`ウィンドウが見つかりません: <名前>` が出る。**ffmpeg が高速で再起動を繰り返さない**こと（1秒→最大15秒へ待ちが伸びる） |
| ブラウザを対象にして**タブを切り替える** | タイトルが変わるため同様に「見つかりません」になる。**別のウィンドウが代わりに映らないこと**（これが映ったら重大な不具合） |
| 対象ウィンドウを**最小化** | 一覧から消える。再取得して選び直せること |
| ウィンドウ未選択のまま「画面共有」へ | `キャプチャ対象のウィンドウが未選択です` |
| 存在しないディスプレイ番号 | UIからは選べない（一覧が実在分しか出さない） |

★2つ目の「別のウィンドウが代わりに映らないこと」は**意図的にそう作った**。
タイトル完全一致でしか掴まないので、似た名前の別ウィンドウを誤って配信する事故が起きない。
不便に見えるが、これは仕様。

### 1-6. モード切替の往復

「画面共有」→「動画」→「ラジオ」→「画面共有」と往復し、
**キューが消費されていないこと**（画面共有はキューを消費しない）と、
毎回ちゃんと復帰することを確認する。

## フェーズ2: VRChat実機での視聴確認（**未確認。ここが本番**）

### 2-1. 起動（トンネル有り）

```bash
Start_Normal.bat
```

配信先URLをコピーする（伏せ字のまま「コピー」を押せば本物がクリップボードに入る）。

- Webリモコン: 「ワールド動画URL:」の横の「コピー」
- ホストPCのGUIウィンドウ: 「🌍 ワールド用 動画URL:」

### 2-2. ワールドで再生

1. VRChatで動画プレイヤーのあるワールドに入る
2. コピーしたURLを貼って再生

| 確認すること | 期待 |
|---|---|
| ワールド内スクリーンに映るか | **← これが今回の主目的** |
| 文字の可読性 | プレゼン資料の文字が読めるか。読めなければ解像度かビットレートを上げる |
| 音声 | タスク22の音声設定をしていれば画面と一緒に出る。**A/Vのズレが無いこと** |
| 長時間 | 10分以上放置して、映像が止まらない・音がずれていかないこと |

★ `-max_interleave_delta 0` を入れてあるのは、ライブ入力のドリフトで
受信側HLSがセグメント出力を止める事故（タスク17で実際に起きた）を防ぐため。
**10分以上の連続配信で止まらないことを必ず確認する。**

### 2-3. 解像度・fpsの当たりを取る

用途ごとに変えて、ワールド内で見比べる。

| 用途 | 出発点 |
|---|---|
| プレゼン・スライド（静止画中心） | 1920x1080 / 10fps / 3000kbps |
| ブラウザ・作業画面 | 1280x720 / 20fps / 4000kbps |
| ゲーム実況（動きが多い） | 1280x720 / 30fps / 6000kbps |

## フェーズ3: 遅延の実測（**未実施**）

HLSは9〜12秒あるので会話は成立しない。TopazChat併用時に何秒になるかを**数値で**取る。

### 測り方

1. **ミリ秒表示のストップウォッチ**をキャプチャ対象の画面に出す
   （LIVE時計オーバーレイは1秒解像度なので、細かい測定には使えない）
2. VRChatを**デスクトップモード**で同じPCに起動し、ワールド内スクリーンが見える位置に立つ
3. ストップウォッチとワールド内スクリーンが**同時に映る**ようにウィンドウを並べる
4. その状態でスクリーンショットを撮る
5. 「実物のストップウォッチの値」−「スクリーンに映っているストップウォッチの値」＝ 遅延

3回以上測って、配信先ごとに記録する。

## フェーズ4: 負荷の実測（**未実施**）

### 測り方

配信中に、別のターミナルで:

```powershell
$n = (Get-CimInstance Win32_Processor | Measure-Object -Property NumberOfLogicalProcessors -Sum).Sum; Get-Counter '\Process(ffmpeg*)\% Processor Time' -MaxSamples 5 -SampleInterval 2 | Select-Object -ExpandProperty CounterSamples | Select-Object InstanceName, @{n='CPU%';e={[math]::Round($_.CookedValue / $n, 1)}}
```

GPU側（NVENCが本当に使われているかの確認も兼ねる）:

```bash
nvidia-smi --query-gpu=utilization.gpu,utilization.encoder --format=csv -l 2
```

### 参考値（2026-09-06 実測・送出ffmpeg単体）

ddagrab → hwdownload → 1080p スケール → NVENC、30fps・4000kbps の構成を単体で回したとき:

- 送出 ffmpeg の CPU: **約 4%**（論理コア全体に対する割合）
- NVENC 使用率: **約 8%**（アイドル時は 0%）

★アプリ本体では **ffmpeg が2本**（送出＋受信/HLS）動く。上の値は送出側だけなので、
実測では合計を見ること。`utilization.encoder` が 0% のままなら NVENC が効いておらず、
libx264 へ退避している（＝CPU負荷が跳ね上がる）。

VRChatを同じPCで動かしながら測ることが重要。VRChat自身がGPUを食うので、
単体測定では出ない競合が起きうる。

## 失敗したときの切り分け

| 症状 | 見るところ |
|---|---|
| `ウィンドウが見つかりません: X` | タイトルが変わった。「一覧を再取得」して選び直す（正常な挙動） |
| `キャプチャ対象のウィンドウが未選択です` | ウィンドウ未選択のまま画面共有モードにした |
| `FFmpeg Error` | 受信側が立ち上がっていない。配信先設定（TopazChat/RTMP）の到達性を疑う |
| `Screen capture sender exited` | 送出ffmpegが死んだ。`vrc_media_streamer.log` の `path=screen_capture` 行の直後を見る |
| `Offline (Receiver Error)` | 受信ffmpegが死んだ。ビットレート過大か配信先の問題 |
| 一覧が空 | ディスプレイ列挙はffmpeg起動を伴う。ffmpegにパスが通っているか確認 |
| 映像が真っ暗 | ウィンドウ指定で対象が最小化・別仮想デスクトップにいる |
| 映像がカクつく | ddagrabは画面が変化しないとフレームを出さない。静止画面では正常 |
| 10分ほどで映像が止まる | A/Vドリフト。`-max_interleave_delta 0` が効いているかコマンドを確認 |

ログの追い方:

```bash
findstr /C:"[Player]" /C:"[Monitor]" vrc_media_streamer.log
```
